# 计划：功能迭代路线

第一版把 magpie 的内核搬了过来（见 [parity.md](../parity.md)）。接下来不再以
“补齐 magpie 的清单”为目标：magpie 往宽处长（80 多个 agent、资料库、搜索和
图像工具、同步、远程、TUI、Web UI、决策模型路由），pansy 往深处长。

**状态：迭代 1 的兼容矩阵、迭代 4（`pansy run`、`.pansy.toml`、按项目记账）、迭代 6 的
agent 清单已实现；另加了连接前的预览、厂商怪癖规则、按 key 的代理和系统钥匙串。其余未开始。**

## 定位

> 每个 agent 的模型，集中在一处。

一句话展开：pansy 是**一个本机网关**，用户把所有 agent 的请求交给它，所以它
首先要**信得过**（转得对、说得清、不碰不该碰的），其次才是功能多。由此得出
五条取舍原则，后面每个迭代都按它们裁剪：

1. **网关是产品，窗口是它的一个客户端。** 命令行、窗口、以后的 TUI 看到的是
   同一个网关的同一份状态。
2. **路由靠数字和规则，不靠模型猜。** 每一次选择都能在 Routing 页上说出
   “为什么是它”。不用一个模型去决定用哪个模型。
3. **动用户的东西，先给看、能撤回。** 现有的不变量（配置原地改一个键、会话
   进回收站）延伸到之后每一个会写用户文件的功能。
4. **长尾是数据，不是内核代码。** 新 agent、新厂商、新价格是一个数据文件或
   一个插件，不需要发版，也不需要改 Rust。
5. **数字留在本机。** 用量、成本、遮蔽记录都不出这台电脑；pansy 自己不接任何
   云端后端。

## 和 magpie 的不同

| 方面 | magpie | pansy | 为什么更合理 |
| :-- | :-- | :-- | :-- |
| 智能路由 | `smart`/`pace`、意图路由，用决策模型 | 按余量、价格、速度、请求特征的规则路由，可预演 | 路由本身不花钱、不加延迟、结果可复现；出错时能查 |
| 换模型的方式 | 改 agent 的全局配置，Profile 整体切换 | 保留；另加 `pansy run`：只给这一个进程设环境变量，按项目选模型 | 不写文件就没有还原问题；两个终端可以同时用不同模型 |
| 更多 agent | 逐个内置（80+） | 声明式清单 + 已有的 agent 插件 | 每个只是“哪个文件、哪个键”，不该占内核和发版 |
| 更多订阅 | 逐个内置（Claude、Antigravity、Grok、Kiro…） | 内置只做“能在原处读到登录”的三个；其余走 provider 插件 | 插件宿主已经在跑；内核不背各家私有接口的维护 |
| 遮蔽 | 规则 + 本地模型 | 只用规则；加按 provider 的策略（本机模型不遮蔽） | 规则找到的每个值都是确定的；模型会漏、会误伤、要占内存 |
| 远程、TUI、Web UI | 三套各自实现 | 一个守护进程 + 一个控制接口，客户端都接它 | 做一次，三处都有 |
| 同步和备份 | 内置 WebDAV、S3、GitHub | 导出成一个加密文件，由用户自己的工具同步 | 不保管用户的云端凭据；少三个后端要维护 |
| 搜索、图像、视频工具 | 内置，经 MCP | 不做 | 不属于“模型网关”；用户装现成的 MCP server 即可 |

## 迭代

每个迭代沿用 parity.md 的完成标准：**网关、命令行、窗口三处都有，并且有
测试。** 大小：S 约一周，M 两到三周，L 一个月以上（一个人）。

### 迭代 1：信得过（M）

目标：协议翻译的正确性从“有测试”变成“有一张公开的表”。

- **兼容矩阵。** 四种协议两两之间 × 流式、工具调用、推理、图片、缓存、
  Codex 的 free-form 工具，每格一组 golden 用例（`pansy-gateway/tests/`），
  由测试生成 `docs/compat.md`。哪一格不支持，写明而不是沉默。
- **真实 agent 的回放。** 六个 agent 各录一组真实请求（去掉内容和密钥），
  作为回归用例；agent 升级后重录即可发现破坏。
- **模型能力表。** 上下文窗口、最大输出、是否支持工具、图片、推理，作为数据
  （`pansy-core/src/models.rs`），厂商模型列表里有的照读，没有的用预设。
- **按能力跳过。** 带图片的请求不发给不看图的模型，超过窗口的不发给装不下的；
  组里直接换下一个，Routing 页写明“因为装不下而跳过”。
- **一句话的错误。** 所有候选都失败时，agent 收到的错误列出试过谁、各自为何
  失败，而不是最后一家的原文。

完成后：README 可以指着 `compat.md` 说“这些组合是测过的”。

### 迭代 2：一个守护进程（L）

目标：落实原则 1。现在窗口自带一个网关，`pansy serve` 是另一个，Routing 的
现场只有窗口的那个有。

- **控制接口。** 网关在本机另开一个只给本人用的接口（Unix socket，Windows
  上命名管道；0600）：状态、trace 的实时流、用量、重新载入配置。
- **窗口接到已在跑的网关。** 启动时先找守护进程，有就接上，没有才自己起；
  关掉窗口与网关无关。
- **`pansy service install|remove|status`。** systemd 用户单元、launchd、
  Windows 计划任务；登录即启动，不依赖窗口。
- **命令行看现场。** `pansy routes --follow`、`pansy top`（正在进行的请求、
  每个账号的状态和休息到何时）。
- **配置热载入。** 文件变了先校验再换；校验失败保留旧的，并在 `doctor` 里报。
- **TUI。** 控制接口有了之后，`nsh --target tui` 托管同一份 TSX。
- **远程。** 窗口和命令行可以指向另一台机器的控制接口（经 SSH 转发）；不另做
  “Remote pansy”。

风险：NSH 的 `pansy/native` 目前直接调用 Rust；改成经控制接口要动
`desktop/native` 的每个调用。先做只读的（状态、trace、用量），写的后做。

### 迭代 3：花得明白（L）

目标：落实原则 2。额度已经读到了（`allowance.rs`），用量已经记了
（`usage/<day>.jsonl` 有 token、耗时、首字时间），还没用来做决定。

- **价格是数据。** 每个模型的输入、输出、缓存读写单价，一个可单独更新的数据
  文件；用量记录加成本，Usage 页和 `pansy usage` 按钱看。
- **预算。** 按 provider、key、agent、项目设每天或每月的上限（token 或钱）；
  到了就像限流一样让它休息到下一个周期，接着用下一个。
- **组的新走法**，都只用本机已有的数字：
  - `headroom`：先用剩余额度最多的；包月的排在按量的前面。
  - `cheapest`：按单价。
  - `fastest`：按近一段时间的首字时间。
- **会话粘住。** 同一段对话在缓存还热的时候留在同一个账号上，除非它失败。
- **按请求特征分流。** 组里的成员可以带条件：有图片、上下文超过多少、是哪个
  agent、是不是它的小模型。条件是字段比较，不是意图判断。
- **预演。** `pansy route explain <model>`：此刻的顺序和每一位的理由，不发
  请求。窗口里是 Routing 页的同一个舞台。
- **按 provider 的遮蔽策略。** 本机模型（Ollama、LM Studio）可以设为不遮蔽。
- **Key 的余额。** 只做有公开余额接口的厂商。

### 迭代 4：按项目（M）

目标：pansy 自己的功能。Profile 是全局的；实际使用是“这个仓库用这个模型”。

- **`pansy run <agent> [--model …] [-- 参数]`。** 用环境变量把这一个进程指向
  网关和模型，不写 agent 的配置。支持哪些 agent 以实测为准（Claude Code、
  Gemini CLI 有环境变量；Codex 用 `-c` 覆盖；其余逐个验证，不行的写明）。
- **`.pansy.toml`。** 放在项目里，写每个 agent 用哪个模型或哪个组；
  `pansy run` 从当前目录往上找。只有模型名，没有密钥，可以提交进仓库。
- **按项目记账。** `pansy run` 发出的进程带一个标记（网关本来就接受本机的
  任何 key，标记放在 key 里），用量、成本、预算可以按项目看。
- **会话页接上。** Sessions 已按文件夹分组；每个文件夹显示它的 `.pansy.toml`
  和花费，“继续”用 `pansy run` 起。

### 迭代 5：一份工具，每个 agent（M）

目标：资料库里最值得做的一半，按原则 3 做。

- **MCP server。** 在 pansy 里登记一次，写进选中的各个 agent 自己的配置：
  用现有的原地编辑和记录（`files.rs`、`jsonedit.rs`、`state.rs`），写之前
  给出每个文件的 diff，撤掉时只拿走 pansy 写的那一项。
- **Skills。** 同样的做法，按各 agent 支持的目录放置。
- **已有的先认领。** 读出各 agent 里已经配好的 MCP server，合并成一份清单，
  由用户决定哪些交给 pansy 管；不认领的不碰。
- **导出和导入。** `pansy export` 把 providers、组、Profile、设置、资料库
  打成一个文件，密钥用口令加密；`pansy import` 读回。同步交给用户已有的
  工具。

不做：指令文件的同步（`AGENTS.md` 已经是各家通用的写法）、subagents（各家
格式差别太大，等它们收敛）。

### 迭代 6：长尾（M，可与前面并行）

目标：落实原则 4。

- **agent 清单。** 把 `agent.rs` 里的 `Kind` 改成数据：一个 TOML 写明怎么
  发现它、配置在哪、什么格式、设哪几个键、支持哪些环境变量。内置的六个先
  改成清单并保持测试通过；之后新增 agent 只提交清单和一个用例。
- **清单和价格、预设一起更新。** 同一条更新通道，带签名，不发版。
- **更多 agent 的会话。** Gemini CLI、Qwen Code、Crush，只读。
- **其余订阅走插件。** 把 magpie-community 里对应的 provider 插件逐个验证，
  在 Plugins 页上标出“已验证”；补上 agent 的 User-Agent 映射。

## 常设小项

每个迭代留约两成时间给 parity.md “Not yet” 里的小件，按用户提到的次数排：
provider 的复制、Use first / Never a fallback、拖动排序、多选删除会话、
Copilot 的 GitHub Enterprise、macOS Keychain 里的 Codex 登录。

## 顺序的理由

- 1 在最前：之后每一项都在网关上加逻辑，先有矩阵才知道有没有改坏。
- 2 在 3 之前：预算、粘住、`fastest` 都是长期运行的状态，应当属于守护进程，
  而不是属于哪个窗口。
- 3 在 4 之前：按项目记账要先有成本和预算。
- 5、6 互不依赖，也不依赖 3、4；人手多时可以提前。

## 明确不做

决策模型路由、本地模型遮蔽、内置的搜索/图像/视频工具、内置云同步、独立的
Web UI、把 80 多个 agent 写进内核。理由见上表；其中任何一项以后要做，先改
这份文件里的原则。
